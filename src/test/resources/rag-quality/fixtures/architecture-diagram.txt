【GOLD:arch-diagram-1】数据流走向：前端埋点 SDK 采集用户行为事件，经 HTTPS 上报到接入网关；网关完成鉴权与限流后批量写入 Kafka 消息队列；流式消费端清洗校验后落 ClickHouse 明细表，T+1 调度任务再从明细表汇总出指标宽表，供报表平台与经营看板查询。链路中任何一环处理失败都会进入重试队列并触发告警，重试耗尽后写入死信表转人工介入；埋点日志同时镜像一份到对象存储，用于回溯补数与审计对账。数据流各环节的消费位点与延迟指标接入了统一监控大盘，明细表写入延迟超过五分钟或 Kafka 消费积压超过阈值都会自动告警；每次报表口径调整都要同步更新宽表的调度脚本与数据字典，并在变更单里记录受影响的看板清单，避免下游报表静默出错。
【GOLD:arch-diagram-2】部署结构：接入层为双 nginx 主备部署，通过 keepalived 维持虚拟 IP 漂移；应用层是 8 节点 Kubernetes 集群，按业务域划分命名空间并配置独立资源配额；存储层为 MySQL 一主两从加 Redis 三节点哨兵，缓存与持久化分离部署；附件与图片走三节点 MinIO 对象存储集群，全链路接入 SkyWalking 做调用链跟踪，应用日志统一采集到 Elasticsearch 集群保留 90 天备查。所有节点通过统一的运维平台管理，发布采用灰度策略：先切百分之五流量观察三十分钟，无异常再全量放开；数据库变更必须走工单审批并在低峰期执行，Redis 键的淘汰策略与容量水位每周巡检一次，MinIO 集群磁盘使用率超过百分之八十时自动扩容并通知值班人员。
