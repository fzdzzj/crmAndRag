# 请求级热路径基线（add-request-hotpath-baseline）

> **性质**：只度量，不改生产行为。检索与摄取主路径各用一份**固定负载**跑两遍——零延迟一遍看**测试侧本地路径**耗时
> （不是纯 CPU，也不是生产业务规则时间），注入延迟一遍把远程调用与数据库从本地计算里分开。调用次数在测试里**逐请求断言**；耗时只记录在本文件，
> **不写入 `ci.yml`，不构成门禁**。
> **日期**：2026-09-25
> **机器**：Windows 11 家庭版（10.0.26200）/ Intel Core Ultra 7 255HX（20 逻辑核）/ 15.4 GB RAM
> **JDK**：Oracle JDK 21.0.9（`D:\develop1\jdk21`，Maven 运行时）；测试经 `mvn test` 执行，**默认挂载 JaCoCo agent**（surefire `@{argLine}`）。
> **基线 HEAD**：master @ `5479f1f`
> **复现**：`mvn -B -ntp -Dtest=RequestHotpathBaselineTest test`（stdout 搜 `HOTPATH` 行；surefire 报告 `TEST-com.slz.crm.quality.RequestHotpathBaselineTest.xml` 的 system-out 有同样内容）

## 1. 负载与测量方法

### 1.1 固定负载（两遍完全一致，写死在测试里）

| 项 | 值 |
|---|---|
| 检索——授权库 | 4 个（kbId 1–4，各 1 份语料文档 ≈11 片） |
| 检索——查询 | 1 条不拆分查询「客户合同续签流程」（不含拆句分隔符，`ConstraintQuerySplitter` 恒单路） |
| 检索——topK | 5 |
| 摄取——子块 | 24 个非空子块（fixed 320/40 下 6600 字符 = ceil(6600/280)） |
| 摄取——父块 | 0 个（fixed 策略不产父块行） |

两遍跑**同一装配、同一输入**，唯一差别是假端口上的延迟：第一遍全 0，第二遍按 §1.2 注入。
生产默认值一个都没改（动态配置用空 Map，全部键走 `RetrievalConfigResolver` / `ContextBuilder` 缺省：
RRF 融合开、父块展开开、查询改写开、邻居开、token 预算 4096）。

### 1.2 注入延迟（合成值，**不是生产测量**）

| 边界 | 每次调用注入 | 实测单次实际耗时* |
|---|---:|---:|
| 嵌入（假 ModelProvider.embed） | 30 ms | ≈31.5 ms |
| 向量检索（假向量库.search） | 20 ms | ≈31.4 ms |
| SQL（假 Mapper selectById/selectList/fulltextSearch） | 5 ms | ≈5.7 ms |

\* 本机 Windows 定时器粒度实测（JDK 21.0.9，`Thread.sleep` 探针）：sleep(20) 与 sleep(30) 都被取整到 ≈31.4 ms
（两个 15.6 ms tick），sleep(5) ≈5.7 ms。**因此实测桶时间 ≠ 名义注入值**；下文占比以实测桶为准，
同时给出名义口径对照（§3.3），两种口径的比较结论一致。

### 1.3 测试侧替换点（不动 src/main）

| 生产构件 | 测试侧替换 | 说明 |
|---|---|---|
| `ModelProvider` | `BaselineModelProvider`：嵌入返回字符分桶确定性向量（32 维、L2 归一化）；**查询改写桩即时返回空串**（回退原查询） | 不调用真实模型；改写 1 次/请求被计数但不注入延迟、不计入远程桶（§1.4） |
| `CrmVectorStore` | `InMemoryVectorStore` + 计数装饰器 | upsert 前补齐 Qdrant payload 读回语义（documentId/chunkId/chunkIndex/text 进 metadata，同 `QdrantReflectionSupport#toPoint`）——否则内存库命中不带 `chunkIndex`，邻居查询不触发，与生产（Qdrant）形状不一致 |
| `DocumentVectorChunkMapper` | 内存 double（Proxy）：insert 分配数字主键，selectById/selectList 解析 QueryWrapper 三列，fulltextSearch 用字符 bigram 重叠分近似 ngram FULLTEXT | 与 `InMemoryDocumentVectorChunkMapper` 同口径；语料全部在授权集合内，不建模授权 JOIN |
| `KnowledgeBaseAuthorizationService` | 子类桩：检索固定返回 4 库、摄取恒可写 | 授权 SQL 不在规格调用形状内，不计桶 |
| `KnowledgeBaseMapper` / `UploadedFileMapper` | Proxy double（insert 回填自增主键） | 等价 MP 自增行为 |
| 存储 / 审计 | `InMemoryFileStorageService`；`GovernanceAuditRecorder(null,null)`（ingest 路径不触发审计） | 零外发、零 Docker |

检索与摄取都走**生产实现**：`KnowledgeRetrievalServiceImpl`（10 参装配：稀疏路 + RRF + 默认重排 + ContextBuilder）、
`DocumentIngestionService.ingest`（存储 → 解析分块 → 嵌入 → DB 快照 → 向量库）。

### 1.4 未观测项（不能成为下一张改动提案的对象）

本测试**没有** JFR、GC 日志、锁等待采样；线程池、队列、超时、JVM 参数零改动、零观测。
锁 / GC / JVM 三个桶**未观测**，按 spec-delta 不参与占比比较、不得被选为下一类改动对象。
另：查询改写 LLM 调用（1 次/请求）用即时桩返回——生产里它是一次真实外呼 RTT，本基线未给它注入延迟，
它也不在远程/数据库/本地三桶内；若后续要归因改写调用，需另案测量。

| 注入延迟（30/20/5） | 235.368 | 240.687 |

### 3.2 摄取热路径

| 遍 | p50 (ms) | p95 (ms) | 嵌入桶实测 (ms) |
|---|---:|---:|---:|
| 零延迟 | 1.221 | 3.759 | — |

### 3.3 三桶对比（注入延迟结果；合成占比仅条件结论）

| 桶 | 实测 (ms/请求) | 实测占比 | 名义口径对照* |
|---|---:|---:|---:|
| 远程（嵌入 1 + 向量检索 4） | **164.426** | **70.4%** | 66.1% |
| 数据库（稀疏 1 + 父块展开 5 + 邻居 5 = 11 次 SQL） | 67.751 | 29.0% | 33.1% |
| 本地（零延迟 p50 墙钟） | 1.410 | 0.6% | 0.8% |

\* 名义口径 = 注入值 × 断言次数（30+4×20 / 11×5），排除 sleep 粒度取整的影响；列出仅为验证结论对粒度不敏感。

**合成占比结论（条件口径，不指定生产改动对象）**：在**本轮预设注入假设**（嵌入 30 ms / 向量检索 20 ms / SQL 5 ms，
实测因 Windows sleep 粒度取整为 ≈31.4/31.4/5.7 ms）与**固定负载**（4 库、topK 5、单路查询、11 次 SQL/请求）下，
远程桶实测占比最高（70.4%），比数据库桶高 **41.4 个百分点**（名义口径 33.0），超过一成（10 个百分点）的比较阈值。
该「单独领先」**仅对所设延迟与固定负载成立**：它是参数化场景的条件结论，不构成生产瓶颈证据——
真实生产 RTT、吞吐、资源占用（锁 / GC / JFR / 线程池）均未观测，**下一类生产优化因素维持未知**。
因此不得据此限定下一张生产改动提案只能改远程（或任何单一类）；逐库并行、批量嵌入、JVM 调参等生产改动同样不据此启动，
合成占比也**不是远程生产优化的授权**。
下一步：先设计**不自动付费**的真实/代表性环境同负载度量方案（分段耗时 + 吞吐 + 资源占用；
外呼与成本节点另获 owner 批准）。若实测分段与本合成场景相反（如数据库或授权/改写桶更高），以实测分段占比为准；
改动前须记录同负载延迟、吞吐与资源占用基线。

**复跑稳定性**（同机同日第二轮）：检索零延迟 p50 1.470 ms、注入 p50 235.235 ms，
三桶 70.6% / 28.8% / 0.6%，合成占比 compare leader=remote、领先 41.8 个百分点——与首轮条件结论一致；
摄取零延迟 p50 1.749 ms、注入 p50 757.316 ms。本表正文数字记录首轮运行。

## 4. 解读边界

- 次数是**断言**（每请求逐次校验，任何形状漂移直接红）；耗时是本机单次运行记录，**跨机不可比**，不入门禁。
- 注入延迟是合成值：它回答「如果远程/SQL 各花这么多时间，占比结构长什么样」，**不能**反过来推断生产 RTT。
- 摄取注入遍只注了嵌入：upsert 未注延迟（规格注入面只有嵌入/向量/SQL），摄取桶除嵌入外可视为本地时间。
- 零延迟遍含 JaCoCo agent 与 JIT 预热残留（各遍前有 30/3/2 轮预热）；同机复跑波动预计在 ±0.5 ms（p50）量级。
- 检索零延迟墙钟（≈1.4 ms）只是**测试侧本地路径时间**（含测试脚手架、JaCoCo agent 与 JIT 预热残留）：
  既不是纯 CPU，也不是生产业务规则时间；授权桩还跳过了授权 SQL，生产请求另有授权与改写外呼。
- 真实瓶颈、吞吐与资源占用**尚未知**：本测试不采集真实 RTT、吞吐曲线或锁/GC/JFR 证据，
  生产瓶颈归因须等真实/代表性环境的同负载分段度量（外呼与成本节点另获 owner 批准）。
- 与 `docs/perf-baseline.md` 的关系：那份是微基准（切分/对齐/拆句 ns 级），本份是请求级形状与占比；
  两份互不覆盖，本份未改动其数字与结论。
