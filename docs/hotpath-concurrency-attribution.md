# 热路径 c8 并发波动受控归因（update-hotpath-concurrency-attribution）

> **性质**：只做测试侧诊断，不改生产行为。在既有 `RepresentativeHotpathBenchmark`（非默认发现入口）之上增加**独立显式诊断模式**：
> 必须同时满足 `REPRESENTATIVE_HOTPATH_MEASURE=1` 与诊断选项（`-Drephot.attribution=…`），缺任一即在**任何容器/装配/模型请求之前**
> fail closed。证据级别与旧报告一致 = **本机真实存储（一次性 MySQL/Qdrant）+ 本地确定性模型桩**，不是生产 RTT；本报告不构成任何
> 生产连接池/线程池/JVM/检索算法的改动授权。
> **日期**：2026-09-26；**基线 HEAD**：master @ `11d83e9`
> **机器**：与旧报告同机（Windows 11 / Core Ultra 7 255HX 20 逻辑核 / 15.4 GB RAM / Docker 29.6.2）
> **旧问题**：`docs/representative-hotpath-measurement.md` §3.2 的 c8 检索 p50 在两执行 × 两轮间 106.8–248.8 ms（约 2.3 倍），标「无法归因」。

## 0. 执行结论（先读这段）

1. **诊断链路真实跑通**：7 条独立命令（3 条件 × 2 独立执行 + 1 条容器画像轮）全部完成，每轮 c8 恒 160 样本、4 授权库、
   topK 5、每请求形状断言与逐库过滤覆盖断言全绿；**逐请求账本与全局计数器逐索引一致（硬断言）全绿，0 失败请求**。
2. **两个设计因素均被排除**（各自只变一个因素、各两独立执行）：
   - **对照 A（预热方式）**：相同预热次数下，单线程顺序预热 vs 8-worker 同步起跑——round 1 照旧慢、round 2 照旧快，
     两方式无可复现差异；
   - **对照 B（阶段顺序）**：c1→c8 反转为 c8→c1——c8 **先于任何 c1 运行**时同样慢（e1 219.4 / e2 160.5 ms），
     「前一相位 c1」不是 round-1 慢的原因。
3. **「执行内首轮 c8 慢」是唯一可复现结构**：6 条干净命令中 **全部 6 个 round-1 c8 p50（160.5–232.2 ms）都慢于全部 6 个
   round-2 p50（114.8–133.5 ms），6/6 完全分离**。旧报告的 106.8–248.8 波动同构（A-r1 248.8 → A-r2 106.8）。
4. **请求级定位（不是全局平均推断）**：慢在**每请求自己的 SQL/存储段**——e1-original 中 corr(单请求端到端, 该请求 sql 段)
   = 0.969（r1）/ 0.994（r2）；8 个 worker 均匀（组内均值极差 1.02–1.03×，无单点拖尾 worker）；调度延迟 0 ms；
   连接获取等待在 r1 升高（p95 195.8 ms vs r2 64.7 ms）但与端到端仅弱相关（0.438/0.611），是嵌套症状而非主因；
   GC 每窗仅 21–49 ms（<2%），CPU 远未饱和，均可排除。
5. **机制层保持「无法归因」**：round-1 效应的物理根因——JIT 竞争路径编译 vs MySQL 缓冲池/全文索引缓存冷 vs Qdrant 段
   预热 vs 宿主机/WSL2 页缓存——**未被隔离**；且 r1 窗口内存在间歇驼峰（e1-original r1 第 6/7 个 20 样本桶均值 687/676 ms
   后回落 131 ms，worker 间仍均匀），跨执行 r1 亦有 160.5–232.2 ms 残差（1.45×）。按规格不改任何生产参数，
   下一轮隔离实验建议见 §8。

## 1. 方法与开关

### 1.1 诊断模式与 fail-closed 边界（全部实测）

| 反例 | 命令要点 | 实测结果 |
|---|---|---|
| 缺独立 opt-in | `mvn -Dtest=RepresentativeHotpathBenchmark test`（无 env） | 入口即抛「缺少独立 opt-in 开关 REPRESENTATIVE_HOTPATH_MEASURE=1」，容器前停止 |
| 诊断选项已传、缺 opt-in | 同上 + `-Drephot.attribution=original` | 同上（opt-in 闸先于诊断闸） |
| 非法诊断值 | env=1 + `-Drephot.attribution=bogus` | 抛「值非法：'bogus'（合法值=original\|warmup-sync\|phase-reversed）」，不静默回落 original |
| 缺镜像 | env=1 + `-Drephot.attribution=original -Drephot.mysql.image=phantom-image:missing` | 抛「本地镜像缺失 [phantom-image:missing]」；`docker images` 复核**未拉取**（0 条 phantom） |

默认 `mvn test` / `mvn verify` / 默认 merge-gate 不发现也不运行该入口（类名不以 Test/IT 结尾，守卫测试锁定）；诊断关闭时
新增代码路径为零参与（计数器钩子为 null），`REPHOT` 原输出逐字节保持历史形状。

### 1.2 三个条件（每次只变一个因素）

| 条件 | 预热方式（c8 预热 8 次） | 相位顺序 | 其余 |
|---|---|---|---|
| `original` | 单线程顺序 | c1→c8 | 与历史完全一致 |
| `warmup-sync` | **8-worker 同步起跑**（每 worker 1 次，次数不变） | c1→c8 | 不变 |
| `phase-reversed` | 单线程顺序（不随顺序变化） | **c8→c1**（摄取相恒在最后） | 不变 |

固定负载（与旧基线逐项一致）：4 个授权库（kbId 1–4）× 单路「客户合同续签流程」× topK 5；摄取 6600 字符→24 子块、
独立库 90001、每样本计时窗口外物理复位；c1 预热 10 + 80 样本、c8 预热 8 + 160 样本（8 worker × 20）、摄取 4 并发 40 样本；
每命令两轮（round 1/2）同 JVM、同容器、同种子。

### 1.3 请求级账本与同窗资源（仅诊断模式）

- 逐请求 JSONL（`target/rephot-attribution/<exec>/requests-*.jsonl`）：seq/worker/req 序号、阶段、开始时刻、端到端、
  16 组分段纳秒（连接获取、SQL 总段、授权/稀疏/父块/邻居/切片/文件、Qdrant search/upsert、嵌入/改写桩、融合/重排/上下文、解析）、
  逐请求 kb_ids、成功/失败与错误。计数器经诊断钩子同线程写入，`finally` 成对清理（线程复用零继承）。
- **一致性硬校验**：每相位结束后账本各分段之和必须逐索引等于全局计数器快照，且账本请求数=样本数，否则该命令直接红。
- 同窗资源采样器（名义 50ms）：进程/系统 CPU、堆、线程数，逐样本记录**实际间隔与单样本开销**；
  容器 CPU/内存仅在独立诊断轮以只读 `docker stats --no-stream` 采集（主矩阵不开，避免扰动）。
- 初始状态清单（`manifest-*.json`）：镜像 digest、容器 id、种子行数、Qdrant 点数、池类型/限制、有效配置、JaCoCo、核数。

### 1.4 复现命令（每条 = 一次独立执行）

```bash
REPRESENTATIVE_HOTPATH_MEASURE=1 mvn -B -ntp -Dtest=RepresentativeHotpathBenchmark \
  -Drephot.attribution=original -Drephot.attribution.exec=e1-original \
  -Drephot.attribution.out=target/rephot-attribution/e1-original test
# warmup-sync / phase-reversed 同式替换；执行 2 用 e2-*；容器画像轮追加 -Drephot.attribution.dockerStats=1
```

### 3.1 检索 c8 端到端分位（全部失败=0）

- e1-original r1：`296 153 182 159 310 687 676 131` —— 首桶慢，中段两个大驼峰，末桶回到 r2 水位；

驼峰期间 worker 间仍均匀（§4.2 取的是全窗），指向**窗口级/宿主级**的全局事件而非单请求事件；

## 6. 结论：观察到的相关性 vs 根因已隔离

**已隔离/已排除（有对照实验或请求级证据支撑）**：

1. c8 波动的主体结构 = **每次执行的第一个 c8 窗口慢、其后窗口收敛**（6/6 分离；r2 档 114.8–133.5 ms 高度稳定）；
2. **不是预热方式**（对照 A 两执行方向不一致、幅度小于轮间差）；
3. **不是 c1/c8 顺序**（对照 B：c8 先跑同样慢）；
4. **不是调度/单点拖尾 worker**（dispatch_delay=0；worker 极差 1.02–1.03×）;
5. **不是 GC、不是 CPU 饱和**（每窗 GC 21–49 ms；进程 ≤5.4/20 核、容器 MySQL ≤64% 单核）;
6. **不是连接池等待为主因**（与端到端弱相关 0.44–0.61；慢请求个体剥掉 conn 后 SQL 段仍慢）——r1 池等待抬升是慢 SQL
   持有连接的**嵌套症状**；
7. 慢的**落点**在每请求自己的 SQL/存储段（corr 0.969/0.994），Qdrant 段次要（r1 超额约 +28 ms），r1 相对 r2 的超额
   ≈ sql +150 ms / 请求。

**仍未归因（保持「无法归因」，不以参数调整代替证据）**：

- round-1 效应的**物理机制**：JIT 竞争路径编译 vs MySQL 缓冲池/全文索引缓存冷 vs Qdrant 段预热 vs 宿主/WSL2 页缓存，
  本轮三个对照都不改变「首个 c8 窗口」这一条件本身，故无法在四者间裁决；
- r1 窗口内的**间歇驼峰**（bucket 均值最高 687 ms）与跨执行 r1 残差（160.5–232.2，1.45×）；
- 因此旧报告的「c8 无法归因」在**机制层维持**：本报告把波动**归位**到「执行内首个 c8 窗口 + 每请求 SQL/存储段」，
  但不宣布根因已隔离，不构成任何生产连接池/线程池/JVM/GC/检索链路改动的依据。

**下一轮隔离实验建议（按性价比排序，均需另行授权开工）**：
1. 单命令跑 ≥4 轮：观察衰减是否单调收敛到 r2 水位（区分「一次性 JIT/缓存」与「持续背景干扰」）；
2. 同容器跨两条 JVM 命令复用（Testcontainers reuse）：把 JVM 冷态与容器冷态解耦；
3. c8 窗口内挂 JFR（仅诊断轮）：把驼峰对齐到编译/去优化或容器外事件；
4. MySQL 侧 `performance_schema` 等待事件只读采样，验证父块/邻居快照 SQL 的等待类型。
