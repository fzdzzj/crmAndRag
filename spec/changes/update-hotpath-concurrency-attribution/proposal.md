# 提案：查明本机热路径 c8 并发档波动来源

## Why

`docs/representative-hotpath-measurement.md` 的 c8 检索 p50 在两执行、各两轮间为 106.8–248.8 ms，修复生产 Qdrant 非空搜索后仍无波动收敛证据；报告明确标为“无法归因”。当前 `RepresentativeHotpathBenchmark` 每轮按 c1→c8→摄取固定顺序执行，c8 的 8 次预热由单线程依次调用 `retrieveOnce`，随后才建立 8 个 worker 同时开跑；窗口内 SQL、连接获取与 Qdrant 耗时主要以全局总量/成功请求数报告，缺少“哪条慢请求在哪一段等待”的关联。因而“JIT/连接池/MySQL/Qdrant”都只是待验证假设，不能拿 c8 数据开启生产调优。

目标是**仅对这一个归因缺口**做受控、本机、零模型外呼实验：区分预热/顺序效应、worker 调度/连接等待以及 SQL/Qdrant 真存储段的请求级贡献。无法解释时继续保留“无法归因”，不以调 JVM/池参数代替证据。

## What Changes

- 在现有非默认发现的 `RepresentativeHotpathBenchmark` 增加**单独显式诊断模式**（保留原模式和报告原数字）：必须同时满足 `REPRESENTATIVE_HOTPATH_MEASURE=1` 和明确指定诊断选项，沿用本地镜像预检、一次性 MySQL/Qdrant、固定 4 个授权 KB/单路查询/topK 5、确定性假 embed/改写，不读密钥、不下载镜像、不运行付费模型。默认 `mvn test/verify/merge-gate` 不启动诊断。
- 先在诊断模式复跑**原序列**（c1→c8、顺序 c8 预热），按请求标记执行编号、轮次、worker、阶段、成功/失败、端到端墙钟。随后仅改变**一个变量**：保持每档预热次数相同，将 c8 预热改为真正 8-worker 同步启动；另以独立实验反转 c1/c8 顺序（重新初始化同等种子与容器状态，避免跨实验携带缓存/集合状态），不得把预热方式和顺序同时改掉再归因。实验条件、冷/暖态、容器状态及重跑顺序必须记录。
- 测试侧捕获请求级等待/服务分段：worker 就绪→同步起跑/调度，连接获取（含池状态可取得时 active/idle/pending）、授权/快照/稀疏 SQL、Qdrant search、改写与嵌入桩、融合/上下文，以及请求端到端；按同一 requestId/worker 关联 p50/p95/p99 和慢尾个体。避免用全局 LongAdder 平均数给单条慢请求“分配”耗时；`ThreadLocal` 如仅在测试侧使用，必须在 `finally` 清理。明确嵌套段与并发重叠，不把总耗时减外呼耗时冒称 CPU。
- 同窗记录已有进程 CPU、堆、GC、线程采样，并核对 CPU load 的多核归一化口径；记录 MyBatis `PooledDataSource` 的实际池类型、限制及连接获取时间分布。容器 CPU/内存和锁等待/JFR 如可无额外依赖且不扰动主测量，可在**单独诊断轮**采集；不可用则标未知而非零。监控开销、JaCoCo 与 Docker 后台活动记入环境条件，不据此调线程池/JVM。
- 增加纯 JVM 的请求关联/分段/安全守卫测试；真实诊断运行至少两次独立命令，每次同一固定样本量（现有 c8 每轮 160）及重复轮次。新建 `docs/hotpath-concurrency-attribution.md`，按对照实验分别给原始统计、请求级分段证据、变化幅度和未解释残差，明确“观察到的相关性”与“根因已隔离”之间的界线。旧两份基线的历史数字不改，只加必要索引（如确实需要）。

## Impact

- **改动范围**：仅 `src/test` 的度量/诊断辅助及守卫测试、新文档和本案规格；不修改 `src/main`、数据库迁移、依赖、动态配置、API、旧测试固定工作量、CI 阈值、线程池/JVM/连接池参数。
- **费用/环境**：一次性本地容器与假模型，CPU/内存占用可见，但不调用真实模型/embedding、不启用真外呼开关、不自动下载镜像。项目原工作树不得触碰。
- **证据边界**：本机 JDK 21 + JaCoCo + Docker 的请求级归因，不等于生产环境；即使某段解释 c8 波动，也不代表生产瓶颈。真实 Provider RTT 及生产拓扑仍未知，须独立授权/同负载验证后才能启动生产优化。

## 验收与停止条件

1. 默认构建不运行诊断；单独选中入口但缺任一开关/镜像时在容器及请求前 fail closed。模型桩仍是唯一 Provider，禁止真实外呼。
2. 对照实验一次只变一个因素；四库/命中/SQL/向量调用次数、有效配置、数据规模相同。若起始状态不同或工作量漂移，只报告“不可比”，不得用新数字解释旧 c8。
3. 逐请求样本与全局计数一致，失败/超时单列；能指出慢请求对应的具体等待/SQL/Qdrant 分段及同步窗口。观察开销、嵌套和未知资源项明确标注。
4. 若两独立执行仍大幅波动、请求级分段不能解释差异，结论保留“无法归因”；只提出下一轮隔离实验，不修改生产热点或调整 JVM/池参数。完成门禁后方可提交合并；不 push、不归档。
