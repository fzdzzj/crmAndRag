# 提案：用同一负载先定位请求时间，再决定改哪一类

## Why

已有 docs/perf-baseline.md 只盘点了 Micrometer，并给切分、对齐、拆句做了微基准。它写明没有流量时那些 timer 是空的，也没有一次请求里的 SQL、嵌入和向量检索次数。在这之前改逐库并行、邻居查询或批量嵌入，都是先选改动、后找证据。

**背景**：
- 检索主路径已知的调用形状是：查询嵌入、按授权库逐次向量检索、稀疏检索、每个命中一次邻居查询。
- 摄取主路径是每个子块一次嵌入，最后一次 upsert。
- 这些只说明可能费时，不能说明哪一类占比最高。

**当前状态**：仓库能重复跑微基准，但不能用同一负载比较业务规则、数据库、远程调用、锁、CPU 和 GC。

**期望状态**：一份固定负载跑两遍。零延迟一遍看测试侧本地路径墙钟（不是纯 CPU）；注入延迟一遍比较指定假设下的远程调用与数据库。记录次数和合成场景延迟；本测试不采集真实资源占用或生产 RTT。本提案不改生产代码，不调 JVM。只有取得同负载、真实或代表性环境的分段耗时与资源证据后，才能决定下一张生产优化提案改哪一类。

## What Changes

- 增加一个 surefire 测试，用假嵌入、假向量库和假 Mapper 跑固定的检索与摄取负载。
- 统计每次请求的嵌入次数、向量检索次数、SQL 次数和写库次数。
- 零延迟与注入延迟使用同一负载。注入值写死在测试里，并在文档中标明这不是生产测量。
- 把结果写入新的 docs/request-hotpath-baseline.md：保留逐请求次数与合成占比，但合成领先仅是参数化场景结论，不能点名生产瓶颈或限制下一案只能改远程。已有微基准文档不改数字、不改结论。
- 锁、GC、线程池、JVM 参数与真实远程/数据库 RTT 均标为未观测。未经测量不开始对应生产优化；后续测量案可将这些桶纳入观测，不预先排除。

## 时间线评估

小。不启动服务，不连 MySQL 或 Qdrant，不调用模型。

## 风险

- 注入延迟的各桶占比由预置的 30/20/5 ms 假设和调用次数决定：即使合成远程领先 41.4 个百分点，也不能宣布生产远程瓶颈。零延迟墙钟亦含测试 double、JaCoCo 与调度，不等于纯 CPU。
- 分位跨机器不可比：次数可以断言，耗时只入文档，不进 CI 阈值。
- 把调用次数下降误写成已经变快：次数下降后仍要用同一负载再跑一遍，耗时没降就回到度量，不继续改别的类。
